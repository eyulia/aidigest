The executive decision: buy vs build
Usually buy
Compute + model + serving
GPU infrastructure, foundation model weights, and inference APIs are almost never built in-house. The economics don't work and the talent requirements are prohibitive for all but the largest tech companies.
Buy or build
Memory & data layer
Vector databases and data pipelines can be bought as managed services (Pinecone, Weaviate) or built on open-source infrastructure. The choice depends on data sensitivity, scale, and whether an existing data team is in place.
Usually build
Application + orchestration
Your business logic, prompts, guardrails, and agent workflows are where your differentiation lives. Most organisations assemble this layer using open-source frameworks (LangChain, AutoGen) rather than building pure from scratch.
What the diagram doesn't show
01
There is no universal consensus on this stack
Different vendors draw these boundaries differently — and often self-servingly. AWS emphasises Bedrock as the natural serving layer and treats everything above it as your problem. LangChain and LlamaIndex want to own your entire orchestration and memory layer. OpenAI is now vertically integrating downward into deployment services. The stack blurs wherever a vendor has commercial interest in blurring it.
02
The layers are not cleanly separated
Unlike the OSI networking model, AI stack layers bleed into each other constantly. Memory bleeds into orchestration. The serving layer bleeds into the model itself (prompt caching, KV cache). Application logic bleeds into prompt design, which bleeds into model behaviour. A clean seven-layer diagram is a useful map — not an accurate description of reality.
03
The middle layers are moving fastest
The memory and orchestration layers barely existed as distinct categories 18 months ago. Stateful agents as a concept is being productised right now — in May 2026. The compute and model layers are relatively stable; the orchestration and memory layers are where most of the churn is. Any stack diagram you see today will be partially outdated within a year.
04
Value doesn't live where the diagram is tallest
The foundation model and compute layers dominate headlines and investment. But for most enterprises, the actual ROI question lives in the application and orchestration layers — specifically, how well your business logic, context design, and agent workflows are built. Most deployments that fail do so not because the model is bad, but because the layers above it are poorly designed.
05
Vendor lock-in compounds as you go down the stack
Switching a UI is straightforward. Switching an agent framework is painful but possible. Switching your foundation model vendor after building deep integrations into their proprietary APIs, fine-tuning pipelines, and data formats is a multi-month project. The further down the stack a vendor dependency sits, the higher the switching cost — and the more leverage that vendor has in future contract negotiations.

Key insight for procurement

When a vendor says their model is now 40% faster or 30% cheaper, ask: did the model weights change, or did something in the inference or runtime layer change? The answer tells you whether you're seeing a genuine capability advance or an engineering efficiency gain — both are valuable, but they're different things.

Speculative decoding, KV cache improvements, and better batching are all inference-time techniques. The underlying model is identical. The same question applies to cost reductions: prompt caching and batch inference can cut costs by 60–90% without touching the model at all. Vendors rarely volunteer this distinction.

Pre-training

Building the model from scratch

Decisions made here — architecture, data sources, vocabulary — are permanent. Changing them means rebuilding the model entirely. This is where labs like OpenAI, Anthropic, and Google spend billions.

Training

Teaching the model to be useful

The model learns from data through gradient descent, with hyperparameters controlling how. RLHF steers it toward helpfulness and safety. These choices shape the model's core capabilities and personality.

Post-training

Refining for specific use

Fine-tuning and RFT adapt a base model to a domain. Quantization and distillation compress it. These techniques sometimes change model weights — making them a middle ground between building and running.

Inference

Running the model efficiently

Inference optimisation techniques — speculative decoding, KV cache, prompt caching — make the model faster and cheaper without changing what it knows. Most vendor "performance" claims live here.

Production runtime

Measuring and governing in production

Evals, observability, guardrails, and A/B testing happen here continuously. This is where quality is maintained over time — and where most enterprise AI deployments quietly fail without it.
